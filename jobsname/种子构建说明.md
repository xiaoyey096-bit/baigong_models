# 典型岗位种子构建说明

> 把 `majors_data/` 的岗位词频榜，归纳成每个专业的「典型岗位名称」种子文件，供 Stage 4（`run_classify.py`）做归类锚点。
>
> **构建方式（2026-08-16 定稿）**：**纯 LLM 看词频榜，脚本化批量**（`name_clusters.py` 逐专业调 GLM，固定 prompt + temperature 0.3 + 断点续跑）。
>
> **为什么从「聚类+LLM」回退**（2026-08-16 对照 eval，3 专业 × 同一 Qwen KNN 管线、同 θ=0.65）：
> 同类岗位家族（护士/口腔护士/护士长/护工）在 embedding 空间余弦 >0.9，HDBSCAN 聚成巨簇 →「一簇一种子」→ 护理只给 3 个种子、覆盖率 84%；纯 LLM 看词频榜给 13 个种子、覆盖率 **96%**。**聚类"定结构"在最需要细分的同质专业上恰好失效**，而词频榜 + 合并/边界规则足够 LLM 稳定辨向。
>
> **种子数量**：**不设上下限，唯一标准是合理性** —— 实质相似的合并，真实不同的方向保留，最终种子之间边界清晰。宽专业自然多、窄专业自然少，不人为配额。
>
> **阈值**：`MIN_JOBS_PER_MAJOR = 100` —— 只有「有效匹配岗位数 ≥ 100」的专业才构建种子（< 100 样本太少，归纳不可靠）。该阈值随甲方需求可能变化，参见 [README.md](README.md) 关键参数表。

---

## 方法演进

| 版本 | 方法 | 问题 |
|------|------|------|
| v1 | 纯 LLM：手工对话面对全量频次榜归纳 | 不可复现、黑盒、质量看运气（换上下文结果就变） |
| v2 | 聚类（BGE+HDBSCAN）定结构 + LLM 定名字 | 同质专业巨簇吞方向：护理 3 种子/84% vs 纯LLM 13 种子/96%，2026-08-16 退役；脚本已删（2026-08-17 清理） |
| **v3（现）** | **纯 LLM 看词频榜，脚本化批量**（固定 prompt + 逐专业 API + 断点续跑） | —— LLM 辨向能力 + 脚本化可复现，兼得两者 |

> v3 与 v1 的本质区别：v1 是**手工对话**（prompt 随口变、无断点、无验收口径）；v3 是**脚本化流水线**（SYSTEM_PROMPT 固化、temperature 0.3、逐专业调用可单独重跑）。

## 输入 / 输出

### 输入（两份）

| 文件 | 作用 | 生成方式 |
|------|------|---------|
| `majors_data/专业匹配岗位统计_{range}.xlsx` | **门槛名单**：筛出「匹配岗位数量 ≥ 100」的专业代码集合 | `stat_by_major.py --range {range}` |
| `majors_data/岗位词频统计_{range}.jsonl` | **归纳素材**：每个专业的全量岗位名频次榜 | `stat_job_freq.py --range {range}` |

> ⚠️ 两份文件必须**同范围**（都是 `{range}`，如 `2026(01-08)`），否则岗位数对不上。

### 输出

```
models/典型岗位名称_gt100_{range}.jsonl
```

文件名含义：`gt100` = 只含岗位数 ≥ 100 的专业；`{range}` = 本次数据范围。两者都标，避免覆盖旧种子。

每行格式（与旧种子完全一致，下游零改）：
```json
{"专业代码": "530701", "专业名称": "电子商务", "典型岗位名称": ["电商运营", "跨境电商运营", "电商客服", "电商美工", "网络销售", "直播运营"]}
```

## 构建流程

```
① stat_by_major.py --range 2026(01-08)
   → 专业匹配岗位统计_2026(01-08).xlsx        （门槛名单）

② stat_job_freq.py --range 2026(01-08)
   → 岗位词频统计_2026(01-08).jsonl            （归纳素材，全量频次）

③ ── 种子归纳（脚本调 GLM，自动批量，6 路并发）──
   export ZHIPUAI_API_KEY="你的Coding Plan key"
   cd models/jobsname/scripts
   python name_clusters.py --range 2026(01-08)          # 默认 coding 后端（套餐 OpenAI 协议端点）
   · 从 xlsx 筛 ≥100 专业，读词频榜取每专业 top-150 高频名（名称×频次）
   · 逐专业发给 GLM 直接归纳：辨方向 → 合并去重 → 边界自检 → 输出一行 JSON
   · 种子数量不设上下限，唯一标准是合理性：边界清晰的颗粒度有几个就给几个
   · 断点续跑：已成功的专业跳过；单专业失败不中断
   → models/典型岗位名称_gt100_2026(01-08).jsonl，供 run_classify.py 使用
   ⚠️ 若 MIN_JOBS_PER_MAJOR 阈值变更，种子需按新门槛重跑
```

> **为什么用 xlsx 而不是直接用频次榜筛 ≥100**：频次榜的「岗位总数」是清洗后去重计数的口径，xlsx 的「匹配岗位数量」是 Stage 3 分组的有效匹配口径。**门槛判断以 xlsx 为准**（与 `run_classify.py` 的 `MIN_JOBS_PER_MAJOR` 同口径），保证「构建种子用的专业」=「归类时会用到的专业」，不会多也不会少。
>
> **为什么只发 top-150**：高频段已覆盖累计频次的绝大多数；低频长尾多为脏名/变体，会稀释注意力。eval 实测 150 足够 LLM 辨出全部真实方向（护理 13 个、新能源汽车 18 个）。

## 归纳 Prompt（已固化进 name_clusters.py）

System Prompt 固化在 [`scripts/name_clusters.py`](scripts/name_clusters.py) 顶部的 `SYSTEM_PROMPT`，User Prompt 由 `build_user_prompt()` 按每个专业的词频榜 top-150 自动生成。改 prompt 须同步本文件。

> ⚠️ 与 v1（纯 LLM 手动对话）的区别：**接入方式**从"手动粘给 Claude 对话"改为"脚本调 GLM API 自动批量"（固定 prompt + temperature 0.3 + 逐专业调用 + 断点续跑），可复现、失败可单独重跑。默认走**智谱 GLM Coding Plan 套餐**端点（OpenAI 兼容协议，用套餐额度）。

### LLM 接入配置

| 项 | 默认 | 说明 |
|----|------|------|
| 词频榜 top-N | **150** | 每专业发给 LLM 的高频名数（eval 实测足够辨向，护理 13 方向 / 新能源汽车 18 方向全覆盖） |
| backend | `coding` | 智谱 **Coding Plan 套餐**的 OpenAI 协议端点（`/api/coding/paas/v4`）；`anthropic`=套餐的 Anthropic 协议端点（`/api/anthropic`，Claude Code 同款接入）；`zhipu`=按量计费（`zhipuai` SDK）；`openai`=OpenAI 兼容（本地/其他云端） |
| model | `glm-5.2` | `--model` 可改；Coding Plan 支持 glm-5.2/5.1 等 |
| API key | 环境变量 `ZHIPUAI_API_KEY` | anthropic 后端也认 `ANTHROPIC_API_KEY`；openai 后端读 `OPENAI_API_KEY`+`OPENAI_BASE_URL`。也可 `--api-key` 传 |
| temperature | 0.3 | 低温度保证可复现 |
| max_tokens | **16384** | **GLM-5.2 强制思考，思考 ~8K token 计入 max_tokens**；给 8192 会被思考挤空正文（~11% 专业「返回为空」的根因） |
| 并发 workers | 6 | `--workers` 可调；强制思考下单次 100~300s，6 路并发把 678 专业压到 ~4h |

> 💡 **关于思考模式（2026-08-15 实测 + 官方文档确认）**：GLM-5.2/5.3 **官方已不支持关闭思考** —— `thinking.type=disabled` 与 `reasoning_effort=none/minimal`（文档写「模型放弃思考」）在 coding/anthropic 两个套餐端点均被忽略，anthropic 协议的 `budget_tokens` 上限同样不生效。应对：**max_tokens 给足 16384**（思考 ~8K + 正文，正文不再被挤空），**速度靠 6 路并发**（单次 100~300s 是思考固有耗时）。
>
> 💡 **关于 Coding Plan**：智谱的 GLM Coding Plan 是订阅套餐，只能在套餐端点用（不能走普通按量计费的 `zhipuai` SDK，否则报 `1113 余额不足`）。脚本默认 `coding` 后端（OpenAI 协议，速度快于 anthropic 端点）；也可 `--backend anthropic` 走 Anthropic 协议端点。如果你用的是按量计费账户（有余额），改 `--backend zhipu` 即可。

### System Prompt

```text
你是「职业教育岗位分析专家」。你会收到一个专科专业的【岗位名词频榜】（岗位名×频次，降序，已截取高频段）。你的任务：直接从词频榜归纳出与该专业真实职业颗粒度数量一致的若干个「典型岗位名称」（数量不设上下限）。

【什么叫典型岗位名称】
该专业毕业生最可能从事的、具有代表性的【通用岗位称谓】。
  1. 是通用名，不是带公司/平台/级别的长尾变体：
     ✓ 电商运营        ✗ 天猫运营专员、亚马逊运营助理、电商运营经理
     ✓ 护士            ✗ ICU护士、手术室护士长、三甲医院护士
     ✓ 软件测试工程师  ✗ 自动化测试工程师(高级)、测试开发
  2. 若高频名本身就是通用名，直接用；
     若高频名都是带修饰的变体，归并/还原为上位通用名：
     电商运营专员 + 电商运营助理 + 电商运营岗 → 电商运营。
  3. 一个典型名要能覆盖一批原始长尾变体，起到归类锚点作用。

【怎么读词频榜】
  · 频次是代表性信号：高频名是该专业的主干职业方向；低频名里可能藏着
    真实但小众的方向，值得辨认，不为频次牺牲真实方向。
  · 同一岗位的多种叫法（护士/口腔护士长/临床护士混排）只算一个方向；
    但【职责确有不同的家族成员要分开】：护士 ≠ 护工（持证上岗 vs 生活照护）、
    护士 ≠ 护士长（临床执行 vs 病区管理）—— 这类颗粒度差异正是要辨的。
  · 明显脏标题不要据其立种子：含公司名、薪资诱饵（"300一天包吃住"、
    "保底8000"）、招聘前缀（"(急招)""【直聘】"）的条目，剥掉杂质后若指向
    已有方向就归入，指向不明就忽略。
  · 宽专业自然多方向、窄专业自然少，不人为配额。

【归纳规则】
  · 数量（不设上下限，唯一标准是合理性）：该专业有几个【边界清晰】的
    职业颗粒度就给几个种子。实质相似的必须合并、真实不同的必须保留：
    既不为凑数增补，也不为精简而牺牲真实方向。
  · 覆盖度：不能全是同一职能，要兼顾该专业的主要职业方向
    （电商 = 运营 + 客服 + 设计/美工 + 销售 + 直播/新媒体）。
  · 频次优先但不唯频次：高频名为主干，补入代表重要方向的低频名。
  · 相近专业趋同（重要）：含义相近的专业，典型岗位名应大致一致；
    但若两者确有可解释的职责侧重差异，保留差异，不为整齐而牺牲准确。

【合并去重规则（重要 —— 每个专业输出前必做）】

种子列表里若两个名存在「包含关系」（一个是另一个的字面子串，或仅差
职业等级/资质/复数后缀），必须逐对判断该合并还是该保留：

  ▶ 必须合并 —— 二者指同一个岗位，只是叫法/修饰不同：
    判定信号（满足其一即合并）：
      · 仅差"员/人员/工/师"等职业通名后缀：保安员=保安人员=安保员 → 保安
      · 仅差"注册/高级/中级/助理/专员"等资质级别前缀，且在本专业语境下
        不构成独立岗位：安全工程师 = 注册安全工程师（注册只是证书）→ 安全工程师
      · 加的行业/领域定语就是本专业默认语境，去掉不丢信息：
        在【化工装备技术】里：设备工程师 = 化工设备工程师 → 设备工程师
        在【建筑工程技术】里：施工员 = 土建施工员 → 施工员
    合并时取【字数最少、且语义完整】的那个（通常是去掉定语的上位通用名），
    频次按两者相加计。

  ▶ 必须保留 —— 字面虽包含，但有独立的职责/技术领域/工种身份：
    判定信号（满足其一即保留）：
      · 是独立持证工种，非"通用名+修饰"：维修电工 ≠ 电工（维修电工专注维修、
        单独持证）；仪表工 ≠ 仪表工程师（操作工 vs 工程师，级别职责不同）
      · 限定了不同的处理对象/技术分支：污水处理工程师 vs 水处理工程师
        （污水特指，水处理是含净水/纯水的上位）—— 在水处理/环境专业里两者并存合理
      · 限定了不同的检验领域：微生物检验员 ≠ 检验员（需无菌/微生物专业技术）
    这种情况两个都保留，它们是不同的归类锚点。

  一句话原则：字面包含只触发审查，不自动合并；
              合并的依据是"同一岗位的不同叫法"，保留的依据是"不同岗位"。

【边界自检（重要 —— 每个专业输出前必做）】
对最终种子列表两两名逐对检查一次边界：
  · 两个名的【主要职责差异】要能用一句话说清（服务对象/核心技能/工作
    产出不同）。说不清差异、或实质只是同一职责的两种侧重 → 合并。
  · 两个名的职责差异一句话能说清、招聘市场上也确实是两类岗 → 保留。
最终效果：种子之间互不重叠、边界清晰；每个原始岗位名归入哪个种子
都应有唯一答案，不存在"两个都像"的模糊地带。

【输出格式（严格）】
逐专业输出，每个专业一行 JSON，顺序与输入一致。不要 markdown、不要解释、
不要代码块包裹，整体即一个合法的 jsonl 文件：
{"专业代码":"530701","专业名称":"电子商务","典型岗位名称":["电商运营","跨境电商运营","电商客服","电商美工","网络销售","直播运营"]}
{"专业代码":"410102","专业名称":"作物生产与经营管理","典型岗位名称":["农业技术员","农艺师","种植技术员","植保技术员","农资销售员","农业技术推广员"]}
...
```

### User Prompt 模板（由 `name_clusters.py :: build_user_prompt()` 自动生成）

脚本对**每个专业单独**生成一份 User Prompt（逐专业调用 LLM），内容 =
专业代码 + 专业名称 + 该专业的**词频榜 top-150**（`岗位名 ×频次`，降序）：

```text
专业代码：530701
专业名称：电子商务
词频榜（前 150 名，按频次降序）：
  电商运营 ×1234
  电商客服 ×987
  美工 ×654
  淘宝运营 ×543
  ...
  直播助理 ×12

请按系统提示词规则，为本专业输出【一行】 JSON。
```

> 门槛（≥100 专业）的过滤已在 `name_clusters.py :: load_inputs()` 完成（读
> `专业匹配岗位统计_{range}.xlsx`），发给 LLM 的专业都是达标专业。
> top-150 是 config 里的 `TOP_FREQ_FOR_LLM`：eval 实测 150 个高频名足够 LLM
> 找全方向（护理 13 方向 / 新能源汽车 18 方向全覆盖）；更长的榜只会稀释注意力。
> 脏标题（"(急招)口腔护士"、"300一天包吃住"）**原样进榜**——系统提示词已教
> LLM 剥杂质归方向、不据其立种子，不预清洗。

## 备注

- **旧种子 `典型岗位名称_gt100.jsonl` / `典型岗位名称_gt100_2026(01-08).jsonl`**：前者为历史人工 + 纯 LLM 手工对话生成（不可复现），后者为聚类+LLM 版（巨簇吞方向，已退役）。均归档保留，不覆盖、不再使用。
- **方法史**：v1 纯 LLM 手工对话（不可复现）→ v2 聚类+LLM 命名（2026-08-16 对照 eval 证明失效，退役）→ **v3 纯 LLM 看词频榜（脚本化）**，演进依据见本文档头部。
- **种子复用**：种子一旦构建，在岗位市场无大变动的前提下可跨季度复用；数据范围大变或阈值调整时重跑。
- **簇对齐 → 种子对齐**：构建完成后可人工抽查相近专业（如作物生产/现代农业/园艺）的种子一致性，明显该一致却不一致的再调；有真实职责差异的不强对齐。

### 构建后验收 —— 合并质量检查（推荐每次构建后做）

「合并去重规则」是构建时的约束，但实际跑下来仍可能有漏网变体或误伤。**每次构建完成后，建议做一遍合并质量验收**，确保种子干净：

**验收步骤**（中性描述，执行方式不限）：

1. **扫包含对**：在每个专业的种子列表内，找出所有「字面包含对」（短名是长名的子串，或仅差级别/资质/通名后缀）。
2. **逐对判定**（套用上面的合并规则）：
   - "同一岗位不同叫法"（仅差通名后缀 / 资质前缀 / 本专业默认语境定语）→ **应合并**，取字数最少语义完整的，腾出名额补新方向；
   - "不同岗位"（独立持证工种 / 不同处理对象或技术分支 / 不同检验领域 / 工/师级别差异 / 管理岗 / 不同业务领域）→ **应保留**。
3. **保留组归档**：把判定为保留的对按原因分档（操作工vs工程师 / 独立持证工种 / 不同技术分支 / 管理岗 / 不同业务领域），便于复核时快速确认逻辑一致。

**执行方式不限定**：可人工逐对、可让构建 LLM 在输出后自查一遍、可由独立复核 agent（与构建者不同视角）再审一次。重点是**有第二视角覆盖盲点**，而非固定某一种实现。
